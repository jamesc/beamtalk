# ADR 0134: Errors in No-Reply Handlers Crash the Actor

## Status
Accepted (2026-10-19). Amends ADR 0065 § "Error contract" for `handleInfo:`; decides cast error semantics, which ADR 0054 left undecided.

## Context

### The problem

A Beamtalk actor receives three kinds of message:

| Kind | Syntax | Reply channel | What happens when the handler raises today |
|------|--------|---------------|--------------------------------------------|
| Sync call | `counter increment` | yes — `gen_server:call` | error is returned to the caller as a value; actor continues |
| Async cast | `runner go!` | none | logged at `warning`, discarded; actor continues with pre-call state |
| Raw message | `handleInfo:` on a `Server` | none | logged at `warning`, discarded; actor continues with pre-call state |

Sync semantics are right and are not touched by this ADR: the error has somewhere to go, and the caller decides. The other two rows are the subject of this ADR. Both are generated by the same `noreply_error_arms` in `crates/beamtalk-codegen/src/core_erlang/gen_server/callbacks.rs` — a `logger:warning` call followed by `{'noreply', State}`.

ADR 0065 chose log-and-continue for `handleInfo:` deliberately:

> Beamtalk bakes this best practice in: errors in `handleInfo:` are logged and the server continues.

The "best practice" cited is the Elixir idiom of ending `handle_info/2` with a catch-all clause:

```elixir
def handle_info(_msg, state), do: {:noreply, state}
```

But that clause tolerates **unmatched messages** — a stale timer tick after a hot reload, a monitor `DOWN` the author forgot about. It does not, and was never meant to, swallow an **error raised while handling a matched message**. In Erlang and Elixir, a `handle_info` clause that matches and then raises crashes the process, exactly like `handle_call` and `handle_cast`. ADR 0065 conflated the two cases and, by swallowing both, bought stray-message tolerance at the price of let-it-crash.

For casts nothing was ever decided. ADR 0054 says the cast *result* is discarded (there is no caller to return it to), and the implementation extended that to the error.

### Why it matters now

While planning the Thousand Island port (`beamtalk-catalina/PLAN.md`), the failure mode became concrete. A connection handler is a `Server`:

```beamtalk
Server subclass: EchoConnection
  state: sock = nil

  handleInfo: msg =>
    msg match: [
      {#tcp, s, data} -> [
        self process: data.                                    // raises on bad input
        (Erlang inet) setopts: s with: #(Tuple withAll: #(#active, #once))
      ];
      {#tcp_closed, _} -> [self stop];
      _ -> nil
    ]
```

If `process:` raises, today the actor survives with its pre-call state — but the socket's `{active, once}` was consumed by the message that arrived and is never re-armed. The connection hangs forever: no close, no crash report, no supervisor restart, nothing for the operator to see beyond one `warning` line. The same shape applies to any `Server` that drives an external resource from `handleInfo:`: a GenStage-style producer that stops producing, a monitor that never re-monitors, a timer loop that never re-schedules.

A library author can work around it by wrapping every callback in `on:do:` and stopping the actor by hand — which is the universal boilerplate ADR 0065 set out to eliminate, reappearing in every serious `Server`.

### Current state

- Codegen: `generate_handle_info` (`callbacks.rs:1727`) and `generate_handle_cast` share `noreply_error_arms`; both log and return `{noreply, State}`.
- Runtime: a `#beamtalk_error{}` raised in dispatch already carries class, selector and stacktrace (`beamtalk_exception_handler`), so a faithful re-raise loses nothing.
- Tests: `stdlib/test/server_handle_info_test.bt` has `testHandleInfoErrorDoesNotCrashServer` and `testHandleInfoErrorPreservesPreCallState` (BT-1457) asserting the current behaviour. No tests assert cast error semantics.
- Users: there are **no `Server` subclasses** in the stdlib or in any Beamtalk package today (`beamtalk-*/src`), only test fixtures. There are **16 `!` cast sites** across packages (exdura 4, symphony 7, watcher 5) and none in `stdlib/src`.
- Docs: `docs/beamtalk-language-features.md` § "handleInfo: Semantics" documents log-and-continue, and § "Unguarded late-slot reads in lifecycle hooks" relies on it to explain why an `UninitializedStateError` in `handleInfo:` never surfaces as a crash.
- Related: `match:` with no matching arm raises `#pattern_mismatch` (BT-3943), so a `handleInfo:` written as a `match:` without a catch-all arm raises on every unexpected message.

### Constraints

- Principle 10 (`docs/beamtalk-principles.md`): "Embrace BEAM's 'let it crash' philosophy — actors crash independently, the supervisor restarts them. No defensive programming."
- ADR 0043: sync calls must keep returning errors to the caller; this ADR must not change that.
- BT-3596: an actor traps exits only when it overrides `terminate:`; the crash path must behave sensibly both ways.
- The change must not reintroduce the footgun ADR 0065 was guarding against: a stray message crashing a server whose author forgot a catch-all.

## Decision

**A message with no reply channel whose handler raises crashes the actor.** This applies to `handleInfo:` on `Server` subclasses and to async `!` casts on any actor. Sync calls are unchanged.

Concretely, the generated `handle_info/2` and `handle_cast/2` re-raise the caught error with its original class, reason and stacktrace instead of logging it. OTP then does what it always does: `gen_server` calls `terminate/2` with the error as the reason, emits a standard crash report, exits the process, and the supervisor applies its restart policy. `onExit:` observers receive the error reason. Nothing in the runtime needs to know the message kind; the behaviour is the gen_server's own.

**Unmatched messages remain tolerated**, by two existing or cheap mechanisms rather than by swallowing errors:

1. `Server>>handleInfo:` keeps its default no-op body. A `Server` that does not override it ignores everything, as today.
2. A new lint, `handleinfo-no-catch-all`, warns when a `handleInfo:` body's outermost expression is a `match:` with no catch-all arm (`_ ->` or a variable pattern). This is the one place where "unexpected message" and "raise" meet, and the fix is one line.

### What it looks like

```beamtalk
Server subclass: PeriodicWorker
  state: count = 0

  initialize =>
    Erlang erlang send_after: 1000 dest: (self pid) msg: #tick

  handleInfo: msg =>
    msg match: [
      #tick -> [
        self.count := self.count + 1.
        Erlang erlang send_after: 1000 dest: (self pid) msg: #tick
      ];
      _ -> nil
    ]
```

Nothing changes for this class: unknown messages hit `_ -> nil`. If `self.count + 1` could raise, the worker would now crash and be restarted by its supervisor, instead of silently never scheduling the next tick.

```beamtalk
Server subclass: Fragile
  handleInfo: msg =>
    msg match: [
      #tick -> [self tick]
    ]
// ⚠ Warning (handleinfo-no-catch-all): `handleInfo:` matches on `msg` with no
//   catch-all arm; any other message will raise `#pattern_mismatch` and crash
//   this server. Add `_ -> nil` to ignore unexpected messages.
```

### REPL session

```beamtalk
worker := FailingServer spawn
worker onExit: [:reason | Transcript show: "exited: ", reason displayString]
Erlang erlang send: worker pid msg: #crash
// Transcript: exited: Error: deliberate handleInfo: error
worker isAlive                                               // => false
```

A supervised instance is restarted:

```beamtalk
sup := WorkerSupervisor supervise
Erlang erlang send: (sup which: FailingServer) pid msg: #crash
// (gen_server crash report in the log, selector handleInfo:, with stacktrace)
(sup which: FailingServer) isAlive                           // => true  (new pid)
```

### Error examples

A cast whose handler raises:

```beamtalk
runner go!                 // method `go` raises
// crash report: ** Generic server <0.213.0> terminating
// ** Last message in was {cast, go, []}
// ** Reason for termination == error: #beamtalk_error{kind = runtime_error, selector = go, ...}
```

The crash report names the selector and carries the Beamtalk stacktrace, which is what the `warning` line carried before; the only difference is that the process is gone and the supervisor knows.

`terminate:` still runs when the class overrides it (which also makes it trap exits, BT-3596), with the wrapped error as `reason`:

```beamtalk
Server subclass: Connection
  terminate: reason =>
    self.sock isNil ifFalse: [(Erlang gen_tcp) close: self.sock]
```

### Single source of truth

The re-raise replaces `noreply_error_arms` in one place; `handle_info/2` and `handle_cast/2` keep sharing it, so the two paths cannot drift. No Erlang-side change is needed: `beamtalk_actor:handle_info/2`'s `handle_linked_exit` already stops the actor on a non-`normal` `'EXIT'`, and a raised error reaches `terminate/2` through `gen_server` itself.

## Prior Art

| Platform | Error raised while handling a no-reply message | Unmatched message |
|----------|-----------------------------------------------|-------------------|
| **Erlang `gen_server`** | process exits with the error; `terminate/2` runs; crash report; supervisor restarts | `function_clause` crash unless a catch-all clause exists |
| **Elixir `GenServer`** | same as Erlang | same; the community idiom is a trailing `handle_info(_, state)` clause, and `use GenServer` injects a default `handle_info` that logs and continues |
| **Gleam OTP `actor`** | the actor crashes (a `panic` is an Erlang error) | impossible by construction: the message type is closed, `Subject(msg)` only carries that type |
| **Akka (classic/typed)** | exception escapes `receive` → supervision strategy, default **Restart** | `unhandled(msg)` → published to the event stream as `UnhandledMessage`; actor continues |
| **Pony** | behaviours cannot raise; partial functions must be handled at the call site | impossible by construction (typed behaviours) |
| **Pharo** | an unhandled error in a forked `Process` opens a debugger; the process is suspended, not continued | n/a — no mailbox |

What we adopt: OTP's error semantics unchanged, which is what Gleam and Akka also converge on (crash → supervision). What we adapt: Elixir's unmatched-message tolerance, delivered as a default no-op and a lint rather than as error swallowing. What we reject: Akka's `unhandled` event-stream channel — Beamtalk has no event bus for it to go to, and a no-op default serves the same purpose.

## User Impact

- **Newcomer.** A stray message still does not crash their server (lint tells them to add `_ -> nil` when they write a `match:`). A bug in their handler now crashes it, with a crash report naming the selector, which is how they find the bug. Discoverable: the lint fires in the editor; the crash shows in `beamtalk test` output.
- **Smalltalk developer.** An unhandled error surfaces instead of vanishing into a log, which is closer to Pharo's debugger-on-error than the previous behaviour was. `onExit:` and `terminate:` remain message sends; nothing about the mechanism is Erlang-shaped.
- **Erlang/BEAM developer.** `handleInfo:` and `!` now mean exactly what `handle_info` and `handle_cast` mean. The ADR 0065 steelman warning ("a half-baked handleInfo: that swallows errors differently from OTP is worse than no handleInfo:") is retired.
- **Operator.** A crash is visible: crash report, supervisor restart intensity, `observer`. A repeated `warning` in a tight loop is not. Hot code reload is unaffected.
- **Tooling developer.** One new lint over the AST (`handleInfo:` method → outermost `match:` send → arm patterns), in the existing `semantic_analysis/validators` family with its own `DiagnosticCategory`. No codegen or LSP surface changes beyond the diagnostic.

## Steelman Analysis

### Keep log-and-continue (status quo, ADR 0065)
- 🧑‍💻 **Newcomer:** "My server never dies; the least scary behaviour while I'm learning."
- 🏭 **Operator:** "No new failure modes on upgrade; nothing that worked yesterday restarts today."
- 🎨 **Language designer:** "A shipped ADR has stability value. Reopening decisions costs trust."

### Crash in `handleInfo:` only; defer casts
- 🎨 **Language designer:** "Scope the change to an abstract class with zero users; gather evidence before touching 16 cast sites."
- 🏭 **Operator:** "The cast flip is the one that can surprise a running system; stage it."

### Opt-in class-side policy (`class infoErrorPolicy => #crash`)
- 🎩 **Smalltalk purist:** "Policy as a class-side message is the Smalltalk way to express it."
- 🧑‍💻 **Newcomer:** "Nothing I wrote yesterday breaks."

### Tension points
- BEAM veterans and language designers split between "both now" and "handleInfo: now, casts later". The decision picks "both now" because the rule is one sentence ("no reply channel ⇒ let it crash") and shipping it with an exception would make the cast case the next ADR; the cast blast radius (16 sites, all in first-party packages) is auditable in an afternoon.
- Operators are the cohort most exposed to the cast flip. The Migration Path below is written for them.

## Alternatives Considered

### Crash in `handleInfo:` only
Smallest change, zero users affected. Rejected because it leaves `!` with the same silent-hang failure mode for exactly the same reason ("no caller to return to"), and the inconsistency would need its own ADR within months. Everything in the Implementation section applies to both paths through one shared helper, so the extra cost is the cast audit, not code.

### Opt-in per class
```beamtalk
Server subclass: Connection
  class infoErrorPolicy -> Symbol => #crash
```
Non-breaking, but keeps the trap as the default: every library wanting OTP semantics must remember to opt in, and a `Server` from a package you did not write cannot be trusted to crash. Policy knobs also multiply (one for info, one for cast?). Rejected.

### Keep as-is; libraries wrap and self-stop
This is the Catalina workaround. It is `on:do:` + `self stop` around every callback — the boilerplate ADR 0065 was written to eliminate. Rejected.

### Treat `#pattern_mismatch` from the outermost `match:` as "unmatched message" and ignore it, crash on everything else
Preserves stray-message tolerance without a lint. Rejected as too magical: it makes the top-level expression form change semantics, hides a real class of bugs (`match:` over a tuple you mis-shaped), and is invisible in tooling. A lint says the same thing at compile time.

## Consequences

### Positive
- `handleInfo:` and `!` have OTP semantics; supervision trees work for `Server`s the way principle 10 promises.
- Libraries driving sockets, monitors or timers from `handleInfo:` get correct failure behaviour for free; Catalina's plan drops its wrap-and-self-stop shim.
- One fewer semantic difference from OTP to document and to warn BEAM developers about.

### Negative
- A breaking change for the 16 existing `!` cast sites if any of their target methods can raise on live input. Each needs a look.
- Two BUnit tests invert; the docs paragraph on unguarded `late` reads in `handleInfo:` must be rewritten (an `UninitializedStateError` there now crashes instead of being skipped — which is the correct behaviour, and the existing `unguarded-late-read` warning already points at the fix).
- A newcomer who writes a `match:` in `handleInfo:` and ignores the lint can crash on a stray message. This is the OTP default and the lint names the one-line fix.

### Neutral
- Crash reports replace `warning` log lines; the information content (selector, reason, stacktrace) is the same.
- ADR 0065's "Error contract" bullet is superseded by this ADR; the rest of 0065 stands.

## Implementation

1. **Codegen** (`crates/beamtalk-codegen/src/core_erlang/gen_server/callbacks.rs`): replace the body of `noreply_error_arms` with a re-raise of `{Type, Reason, Stacktrace}` (`erlang:raise/3`) so class and stacktrace are preserved; keep the arm shared by `handle_info/2` and `handle_cast/2`. Update the doc comments on `generate_handle_info` / `generate_handle_cast` and the Core Erlang snapshot tests.
2. **Lint** (`crates/beamtalk-core/src/semantic_analysis/validators/`): add `handleinfo_catch_all_validators.rs` with `DiagnosticCategory::HandleInfoNoCatchAll`: for each method named `handleInfo:` whose outermost expression is a `match:` send, warn unless some arm pattern is a wildcard or bare variable. Register in `validators/mod.rs`.
3. **Tests**: in `stdlib/test/server_handle_info_test.bt` replace the two BT-1457 tests with `testHandleInfoErrorCrashesServer` (uses `onExit:` to observe the reason) and `testSupervisedServerRestartsAfterHandleInfoError`; add `stdlib/test/actor_cast_error_test.bt` for the cast path; a lint test over a fixture with and without `_ ->`.
4. **Docs**: `docs/beamtalk-language-features.md` § "handleInfo: Semantics" and § "Unguarded late-slot reads in lifecycle hooks"; `docs/ADR/0065-*.md` Status line gains "Error contract amended by ADR 0134"; `docs/ADR/README.md` index row.
5. **Cast audit** (Migration Path).

Affected components: codegen, semantic analysis (lint), stdlib tests, docs. No parser, runtime or REPL changes. Size: M (BT-3953).

## Migration Path

- **`Server` subclasses:** none exist outside stdlib fixtures. A future `Server` whose `handleInfo:` is a `match:` gets the lint; add `_ -> nil`.
- **Async casts:** audit the 16 `!` sites in `beamtalk-exdura`, `beamtalk-symphony` and `beamtalk-watcher`. For each target method ask: can it raise on data it receives at runtime? If so, either (a) the raise is a bug and crashing is correct — leave it, the supervisor restarts the actor; or (b) the failure is expected and should be handled — catch it in the method with `on:do:` and record it in state, as you would for a sync method returning a `Result`. Expect (a) to be the common case.
- **Operators:** after upgrading, a `Server` or cast-driven actor that used to log `warning`s repeatedly will now show as restarts in its supervisor. That is the signal the warnings were hiding.
- No deprecation period: the behaviour ships with the implementation issue, with a changelog entry marked **breaking**.
